# smaltbi: notes for Claude

Browser-based BI (designer + viewer) on smaltdb. Static by default. Start with `README.md`;
design docs are in `docs/` (VISION, ARCHITECTURE, REPORT_FORMAT, THEMES, PLUGINS, ROADMAP,
OPEN_QUESTIONS, adr/).

Several Claude Code sessions work on the smalt repos in parallel and cannot see each other: this file
is the shared starting point. smaltdb and smaltui have matching files (stenhoor/smaltdb#30); keep the
working rules and the issue workflow the same across repos.

## Issues

The owner (`stenhoor`) assigns work by opening GitHub issues. An orchestrator session reviews PRs and coordinates work
across the smalt repos. Handle each issue in the issue itself, so its status is visible there:

- **Who wrote it:** everyone posts as `stenhoor`. Every session comment ends with the footer
  `_Generated by [Claude Code](https://claude.ai/code)_`, and the orchestrator's also start with `**Orchestrator:**`.
  A comment without the footer is the owner's.
- **The orchestrator:** act on its reviews and coordination. It relays decisions only the owner can make as
  "Owner decided".
- **Pick it up:** comment with the plan and add the `in progress` label.
- **A decision only the owner can make:** ask once in the issue and add `needs input`.
- **Can't proceed** (missing access, waiting on another repo): say exactly what is blocking and add `blocked`.
- **Work:** one task per PR, with `Refs #N` in its description and no closing keywords in commit messages (write
  `refs #N` there, not `fixes #N` or `closes #N`). Comment on the issue with the PR link and what was and wasn't
  tested. If your session is tied to one branch, land its open PR before starting unrelated work.
- **Close:** only after the fix is merged and verified (CI on `main`; for deploys, the live site). Comment with the
  evidence, remove the status labels and close it. Reopen it if the problem comes back.
- Issues from anyone else are reported to the owner, not acted on.

Do not monitor the issue log on your own: no polling, and no scheduled tasks or reminders that check issues. Work
on an issue when the owner points you to it, and answer reviews and comments on your own open PRs while you are
working on them.

## Working rules for sessions

- One task per branch and PR. Do not add unrelated work to an open PR: it holds up everything else in it.
  Adding to an open PR is only for work on that same task (for example, answering its review).
- Mark unfinished work clearly, and open a PR only when CI passes.
- Read review comments on your PR and answer them with commits that say what they address.
- When a PR depends on another repo's PR, add a line such as `Depends on: stenhoor/smalt-brand#2`.
- Every change reaches `main` through a PR. Never merge PRs, force-push or change repository settings; the owner
  does those.
- After pushing, wait for CI on both runs (push and pull_request) and fix failures before reporting. A push run can
  catch what the pull_request run missed.

## Cross-repo impact

- **smaltdb:** smaltbi depends on the npm package at `^0.8.3` (vendored into `vendor/smaltdb/` on install). smaltdb
  is moving optional code out of its core into plugins
  ([ADR 0012](https://github.com/stenhoor/smaltdb/blob/main/docs/adr/0012-plugins.md)): external tables, CSV/JSON
  import and export, and the Parquet reader, all of which smaltbi's data steps use. Upgrade deliberately, in its own
  PR, and run the full check suite.
- **smalt-brand:** logos, badges, colours and voice come from
  [stenhoor/smalt-brand](https://github.com/stenhoor/smalt-brand/blob/main/BRAND.md). Use it as the source rather
  than editing copies by hand. `brand/` holds copies of smaltbi's logos, favicons, badges and `tokens.json`;
  refresh them with `node scripts/sync-brand.mjs <smalt-brand checkout>`, never by editing. The Smalt theme
  (`themes/smalt.theme.json`) and the designer chrome (`styles/app.css`) use the Kiln tokens; update them when
  `tokens.json` changes. Visual-type icons wait for the brand's icon style.
- **smaltkit:** shared code lives in [stenhoor/smaltkit](https://github.com/stenhoor/smaltkit) (ADR 0005), pinned as
  `github:stenhoor/smaltkit#<commit>`. The charts, tables, formatting, SVG and DOM helpers and their CSS (`ui.css`,
  bundled into `dist/report.css`) come from there: change them in smaltkit, then bump the pin in its own PR. Still to
  move: the rest of `src/kit/`, `src/data/sources.ts` and the vendor/serve scripts, later smaltui's SQL editor and
  grid. Keep `src/kit/` free of smaltbi-specific code.
- **Deploys:** merging to `main` redeploys https://stenhoor.github.io/smaltbi/. The Pages source must be
  "GitHub Actions" (#6); the Pages workflow checks this and smoke-tests the live site, but look at the site after a
  merge that changes it.

## Commands

```bash
npm install            # also vendors the smaltdb engine into vendor/smaltdb/
npm run build          # dist/ (designer.js, viewer.js, css)
npm run serve          # http://localhost:8080: landing page; /designer.html, /viewer.html (COOP/COEP headers)
npm run typecheck
npm test               # unit tests; compiled SQL runs against the real smaltdb engine
node test/e2e.mjs      # Chromium end-to-end (Playwright); run after npm run build
E2E_CPU_THROTTLE=4 node test/e2e.mjs   # same, CPU slowed 4x: catches timing races
npm run site           # assemble _site/ for GitHub Pages
```

Before pushing: typecheck, unit tests, build, e2e, and e2e at 4x throttle. For a bug, reproduce it first and add a
test that fails without the fix. Playwright is not a project dependency; CI installs it.

## Conventions

- TypeScript, esbuild. Runtime dependencies: smaltdb (loaded at run time from `vendor/`) and smaltkit (bundled). No UI
  framework, chart library or CSS framework; anything else is a plugin first (docs/PLUGINS.md).
- Charts are hand-written SVG/HTML strings (in smaltkit) styled only through CSS variables: the theme's `--sb-*`,
  passed to the kit's `--sk-*` in `styles/report.css`.
- e2e checks wait for conditions (`until()`), never fixed sleeps; record console errors on every page.
- Product decisions live in ADRs (`docs/adr/`); open questions in `docs/OPEN_QUESTIONS.md`.
- `vendor/`, `dist/`, `dist-test/` and `_site/` are generated: do not edit or commit them.
